# Modelo físico

Sistema para Venta de Computadoras. Implementación en PostgreSQL.

El script ejecutable es `database/01_ddl.sql`. Este documento explica las decisiones que no se ven con solo leer los nombres de las columnas.

## Motor y esquema

- Motor: PostgreSQL 14 o superior.
- Esquema: `public`, el esquema por defecto de la base `venta_computadoras`.
- Codificación esperada de la base: UTF-8, para conservar los nombres con tilde.
- Las cinco tablas se crean en una transacción. Si alguna sentencia falla, PostgreSQL revierte también los `DROP` y deja el esquema anterior intacto.

## Identificadores

Las claves primarias son `INTEGER GENERATED BY DEFAULT AS IDENTITY`.

Se usa `BY DEFAULT`, y no `ALWAYS`, porque la carga de prueba inserta identificadores fijos (el proveedor 1, la venta 1, y así sucesivamente) para que las consultas del curso sean reproducibles. Después de esa carga, `02_dml.sql` mueve cada secuencia hasta el máximo insertado. Las altas hechas por la API omiten el id y reciben el siguiente valor.

## Importes

Precios, subtotales y totales son `NUMERIC(10,2)`.

`NUMERIC` es un decimal exacto. `FLOAT` y `DOUBLE PRECISION` no se usan porque el redondeo binario puede alterar céntimos. El máximo representable es 99 999 999.99, suficiente para los precios y totales de este caso.

El subtotal no se deja solo a cargo de la aplicación. La tabla exige:

```sql
CHECK (subtotal = cantidad * precio_unitario)
```

PostgreSQL rechaza una línea cuyo subtotal no coincida con esa multiplicación.

## Texto, teléfono y documento

Teléfono y documento son `VARCHAR`, no numéricos. Un teléfono puede incluir un guion y un documento no debe perder ceros a la izquierda si en el futuro se ampliara el formato. El documento de este proyecto se valida con 8 a 12 dígitos, que cubre el DNI de 8 dígitos usado en los datos de prueba.

El correo del proveedor y el documento del cliente tienen restricción `UNIQUE`. PostgreSQL crea un índice único para cada una.

## Claves foráneas e índices

Toda clave foránea está declarada con nombre, `ON UPDATE CASCADE` y `ON DELETE RESTRICT`.

PostgreSQL no crea solo un índice sobre la columna que referencia a otra tabla. Por eso el DDL agrega:

| Índice | Columna |
| --- | --- |
| idx_productos_id_proveedor | productos.id_proveedor |
| idx_ventas_id_cliente | ventas.id_cliente |
| idx_detalle_venta_id_venta | detalle_venta.id_venta |
| idx_detalle_venta_id_producto | detalle_venta.id_producto |

Esos índices sostienen las consultas de `03_consultas.sql` y las búsquedas de la API.

La pareja única `(id_venta, id_producto)` evita dos líneas del mismo producto en una venta. La cardinalidad “un producto aparece en muchos detalles” sigue siendo válida porque esos detalles pertenecen a ventas distintas.

## Venta y stock

La regla “una venta tiene al menos un detalle” no se implementa con un trigger. Mientras la transacción inserta la cabecera, la venta todavía no tiene líneas; un trigger de fila impediría ese orden sin aportar nada que la transacción no resuelva. La garantía queda en dos lugares:

- `POST /api/ventas` rechaza una lista vacía y confirma la venta solo después de insertar sus detalles.
- `02_dml.sql` aborta la carga si alguna venta queda sin detalle o si los totales no cuadran.

El total se guarda en `ventas.total` para no recalcular el historial en cada listado. Su valor confirmado es la suma de `detalle_venta.subtotal`. Dentro de la transacción la cabecera se inserta primero con total 0, porque el id de la venta hace falta para las líneas y el `CHECK` permite cero. Antes del `COMMIT` ese total se reemplaza por la suma real. Ninguna otra sesión ve el cero: el cambio todavía no está confirmado.

El precio de cada línea se lee de `productos.precio` con la fila bloqueada. El cuerpo de la solicitud no puede fijar el precio.

## Concurrencia

El nivel de aislamiento es el predeterminado de PostgreSQL, `READ COMMITTED`, más bloqueos de fila.

1. `SELECT ... FROM clientes WHERE id_cliente = $1 FOR SHARE` impide que otra transacción borre al cliente mientras se registra la venta.
2. Los productos se bloquean con `SELECT ... FOR UPDATE`, de uno en uno y en orden ascendente de `id_producto`. El orden fijo reduce el riesgo de interbloqueo cuando dos ventas tocan los mismos productos.
3. Si la cantidad pedida supera el stock bloqueado, se hace `ROLLBACK` y se responde con error.
4. El descuento usa `UPDATE ... SET stock = stock - cantidad WHERE stock >= cantidad`. Si no se actualiza alguna fila, también se revierte la transacción.

Dos solicitudes simultáneas no pueden descontar el mismo stock: la segunda espera el bloqueo, vuelve a leer el stock ya descontado y falla si ya no alcanza.

## Reinicio del entorno

| Acción | Efecto |
| --- | --- |
| Ejecutar `01_ddl.sql` | Borra y vuelve a crear las cinco tablas |
| Ejecutar `02_dml.sql` | Vacía las tablas con `TRUNCATE ... RESTART IDENTITY` y carga otra vez los datos de prueba |
| Ejecutar `03_consultas.sql` | Solo consulta. No modifica datos |

`02_dml.sql` es idempotente: ejecutarlo de nuevo no duplica filas. No debe ejecutarse a medias a mano, porque el descuento de stock asume el stock inicial insertado en ese mismo script.

## Lo que queda fuera de la base

No hay tablas de usuarios, roles, comprobantes ni categorías. La API mínima que usa estas tablas está en `src/` y sus rutas se documentan en `routes/README.md`.
